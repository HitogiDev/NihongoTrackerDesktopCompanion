# Spike: hoshidicts as the dictionary engine

Feasibility check, two passes: the first answered "does it build and work", the
second closed the gaps it left — per-line latency, the renderer inventory, the
crate boundary, supply chain and build hygiene. Nothing here is a feature; the
branch exists to answer questions with numbers.

- Upstream: `github.com/Manhhao/hoshidicts`, branch `main-mit`, commit `af99b55`
  (2026-04-27), MIT.
- Everything lives in **`crates/nihongo-dict/`**, a standalone crate with no
  Tauri in it. The desktop app consumes it as a path dependency; the same crate
  is what an HTTP service for the web texthooker would link.
  - `vendor/` — hoshidicts as a git submodule
  - `cpp/shim.{h,cc}` — the cxx shim
  - `src/lib.rs` — the bridge plus a safe `Dictionary` wrapper (LRU, warm-up)
  - `src/bin/dict_probe.rs`, `src/bin/dict_bench.rs` — probe and benchmark
  - `NOTICE` — attribution obligations that travel with any binary
- The app crate keeps `build.rs` at `tauri_build::build()` and knows nothing
  about C++.

## How to reproduce

```bash
git submodule update --init --recursive --depth 1

cd crates/nihongo-dict
# On Windows, point at the MSVC cmake/ninja rather than the MSYS2 ones on PATH.
CMAKE="…/CMake/bin/cmake.exe" NINJA="…/Ninja/ninja.exe" cargo build --release

./target/release/dict-probe import jitendex-yomitan.zip ./dicts
./target/release/dict-probe lookup 食べさせられなかった 200 "./dicts/Jitendex.org [2026-08-11]"
./target/release/dict-bench sentences.json "./dicts/Jitendex.org [2026-08-11]"
```

No manual patch step: `build.rs` applies the MSVC fix itself (see below).
`sentences.json` comes from `structured-content-census.mjs`, which also produces
the node inventory.

Linux is exercised in containers so the answer is about a clean checkout rather
than about this machine: `build-linux.sh` and `build-linux-portable.sh`.

## Does it build on both platforms?

Yes, on both, and the `cxx` binding links on both toolchains. Since the second
pass this is true with **no manual steps**: `cargo build` in
`crates/nihongo-dict` is the whole procedure.

| | Result | Toolchain | Clean C++ build |
|---|---|---|---|
| Linux | Builds unpatched — verified against a pristine checkout | GCC 15.3, CMake 3.31.6, Ninja | 234 s |
| Windows | Builds **with one source patch and two compiler flags** | MSVC 14.50 (VS Build Tools 2026), CMake/Ninja bundled with VS | 224 s |

What Windows needed, all three mandatory and none of them optional polish:

1. `/utf-8`. The deconjugation rules are a 35 KB UTF-8 raw string literal.
   Without the flag MSVC decodes the source with the system code page — CP932 on
   this machine — which mangles the Japanese and then fails with
   `error C2001: newline in constant`.
2. `/Zc:__cplusplus`. Otherwise MSVC reports `__cplusplus == 199711L`, utfcpp
   hides its C++17 API, and `text_processor.cpp` cannot find
   `utf8::utf8to32(string_view)`.
3. A patch to upstream: `error C2026: string too big`. MSVC caps a single string
   literal at 16,380 bytes and the rules literal is 35 KB. The patch splits it
   into five adjacent literals, which the compiler concatenates (the limit on
   the concatenated result is 65,535 bytes, so 35 KB fits). Kept as
   `patches/0001-msvc-split-string-literal.patch`, generated by
   `split-rules-literal.mjs`, 9 lines changed.

   **`build.rs` now applies it**, so a clean checkout builds with nothing but
   `cargo build`. It is idempotent — a tree that is already split is left alone,
   which also covers the day upstream merges the change — and it falls back to
   splitting the file in place if `git apply` is unavailable, so the build never
   depends on a working git. Verified from a pristine submodule: one literal
   before, five after, build green.

   A PR against upstream is written up in `patches/UPSTREAM-PR.md`, ready to
   send. **It is not opened**: this environment has no `gh` and no GitHub
   credentials. GCC is indifferent to the change (verified: the pristine header
   and the split one both build on GCC 15), so it costs upstream nothing.

One more friction point worth knowing before anyone tries this: `cmake` on PATH
here is MSYS2's, and letting it choose its own compiler produces MinGW objects
that cannot link into an MSVC Rust binary. `build.rs` therefore pins both the
generator (Ninja) and the compiler, copying the MSVC environment out of
`cc::windows_registry` so no vcvars shell is needed.

### The Linux baseline is now CI configuration, not a decision

Building needs **GCC 14 or newer**: the library itself — not just its CLI — uses
`std::ranges::to` (`src/query.cpp`, `src/lookup.cpp`,
`src/json/yomitan_parser.cpp`), which GCC 13 lacks. Ubuntu 24.04 LTS ships GCC 13,
so the LTS cannot *build* it.

It can run it. Built in a `gcc:14` container with `-static-libstdc++
-static-libgcc` (`build-linux-portable.sh`) and then executed in a stock
`ubuntu:24.04` container:

```
builder: g++ (GCC) 14.4.0            binary: 3.42 MB
target:  Ubuntu 24.04.4 LTS, GLIBC 2.39, no g++ installed
ldd:     linux-vdso, libm.so.6, libc.so.6, ld-linux  — no libstdc++
GLIBCXX symbols referenced: 0
highest glibc symbol required: GLIBC_2.38   (target has 2.39)
$ hoshidicts-cli deconjugate 食べさせられなかった
deconjugations for: 食べさせられなかった length: 10
found 75 candidates
```

So: build in a newer container, ship to the LTS. The one thing to pin is the
builder image — glibc symbols are taken from the builder, and 2.38 already sits
one release below the target's 2.39. A builder newer than the oldest target
distro will eventually break this, so the CI image needs a version, not `latest`.

Static-library size is misleading; the linked binary is the number that matters,
and **about 1 MB** of engine is what the app would carry on Windows. The portable
Linux binary is larger because the C++ runtime is inside it, which is the point.

The cost that is *not* in that table is build time. The crate builds clean in
**1 m 40 s** on this machine, C++ included. When the C++ build sat inside
`src-tauri/build.rs` it landed in front of the whole app and a clean release
build took **81 minutes**, of which the C++ was under 4 — an argument for the
separate crate quite apart from the HTTP service.

## Jitendex: import and lookup

| | Linux (container) | Windows (through the cxx binding) |
|---|---|---|
| `jitendex-yomitan.zip` | 38,698,313 B (36.9 MB) | same |
| Imported on disk | 189,945,319 B (181.1 MB), 7 files | identical, byte for byte |
| Import time | 11.0 s, peak RSS 181 MB | 15.4 s |
| Terms / media | 435,448 terms, 250 media files | same |
| Opening the dictionary | — | 39.9 ms |

The imported form is `blobs.bin` (163.8 MB), `hash.table` (12.5 MB),
`media.bin` (4.8 MB), plus `index.json`, `media.idx` and `styles.css`. Roughly
**5× the zip**, which is the cost of a memory-mappable format: both Windows
(`CreateFileMapping`) and Linux (`mmap`) map the blobs instead of loading them.

### Resolving a whole line — the number that decides the HTTP service

500 real Japanese sentences, 43.1 characters on average (min 35, max 68). They
are Tatoeba example sentences lifted out of Jitendex itself, so the register is
modern and colloquial rather than synthetic. Windows, release, machine otherwise
idle, one thread, after warm-up. `dict-bench` reproduces all of it.

**One offset — what a hover actually asks for.** 5,234 calls:

| | mean | p50 | p95 | p99 | max |
|---|---:|---:|---:|---:|---:|
| single offset, no cache | **2.62 ms** | 2.38 | 5.39 | 7.72 | 58.97 |

**Every offset of a line — what pre-resolving a line costs.** 500 lines:

| | mean | p50 | p95 | p99 | max | CPU per 1,000 chars |
|---|---:|---:|---:|---:|---:|---:|
| no cache | **127.3 ms** | 107.8 | 234.4 | 555.2 | 957.6 | 2,954 ms |
| LRU in front | 123.2 ms | 109.4 | 219.6 | 417.6 | 631.6 | 2,859 ms |

**The LRU barely does anything: 7.4 % hit rate** (1,600 hits in 21,542 lookups)
over 500 distinct lines, and **3.1 %** within a window of 10 consecutive lines.
First line of a window 120.6 ms, lines 2–10 127.2 ms — no warm-up effect at all.

That result is worth being precise about, because the premise behind the
question was reasonable and the data says the lever is somewhere else. Japanese
does repeat vocabulary, but the engine is not keyed on vocabulary: every offset
hands it a different *suffix*, and two occurrences of the same word in different
sentences produce different suffixes. Keying the cache on the whole input is
therefore keying on something that is nearly unique.

The obvious refinement does not help either. The engine never looks further than
`scan_length` (16 characters) past the offset, so truncating the cache key to 16
characters is exact, not approximate — and it produced **the same 1,600 hits**,
to the entry. Within their first 16 characters, real suffixes essentially never
coincide.

What this means for the service:

- **Interactive lookup is comfortable.** 2.6 ms average, 7.7 ms at p99, for the
  one offset under the cursor. A popup can call straight through with no cache.
- **Pre-resolving whole lines is not.** 2.9 seconds of CPU per 1,000 characters,
  single-threaded, means one core sustains roughly 340 characters per second.
  A shared service that eagerly resolves every line it is sent will spend
  essentially all of its CPU there.
- **Caching lookups is not the fix; not doing the work is.** Resolve on demand,
  one offset per hover. If lines must be pre-resolved, the cache has to be keyed
  on something that actually repeats — the matched substring or the lemma, i.e.
  a layer above this API — and that is a design decision, not a tuning knob.
- Cost scales with candidate count, not with length: see the per-word table
  below, where `食べた` (3 chars) costs more than `蒼の彼方` (4 chars).

### Lookup latency by input

Measured in-process on Windows, 200 runs each, after warm-up. Latency tracks the
length of the string handed in, because `Lookup` scans substrings from
`scan_length` (16 by default) down to 1, deconjugating each one:

| Input | Length | Results | Warm average |
|---|---|---|---|
| `猫` | 1 | 2 | **0.16 ms** |
| `蒼の彼方` | 4 | 2 | **1.40 ms** |
| `食べた` | 3 | 4 | **9.53 ms** |
| `食べさせられなかった` | 10 | 4 | **30.24 ms** |

The first lookup after opening cost 491 ms — page faults on the freshly mapped
`blobs.bin`. `Dictionary::warm_up()` now pays that at start-up instead, by
looking up eight common function words that pull the hot pages in; after it, the
first real lookup is an ordinary one. It is one call after `add_term_dict`.

So the honest summary is: a hover on a word is **sub-millisecond to a few
milliseconds**, and the worst case measured, a ten-character fully conjugated
verb chain, is 30 ms. `食べた` costing more than `蒼の彼方` shows what drives it:
not length, but how many deconjugation candidates the string produces and how
many glossaries have to be zstd-decompressed. There is no result cache; adding
one at our level would be straightforward.

The answer is correct, and identical on both platforms:

```
食べさせられなかった
  past -> (ka stem) -> negative -> (mizenkei) -> passive/potential -> causative
食べる たべる
```

The deconjugator alone offers 75 candidates for that string; the lookup then
filters them by the part-of-speech tags in the dictionary, which is what turns
75 guesses into 4 results. The other three results are 食 read three ways —
correct behaviour, since it also scans shorter substrings.

## Does the API expose what we need?

Yes for the three things asked, with caveats.

**Deconjugation — yes.** `Deconjugator::deconjugate` returns each candidate with
`text`, `tags` and `process`, the chain in order. `LookupResult` carries
`matched`, `deinflected` and the same `process`, so the UI can show the road from
surface form to lemma.

**Frequency — yes.** `add_freq_dict` + `query_freq`, and `get_freq_dict_order()`
exposes the order so the caller can choose which dictionary's number to display,
like Yomitan does. Frequency is also a tiebreaker in the result sort.

**Multiple dictionaries with priority — partially.** Priority is *insertion
order* and nothing else:

- Glossaries inside one entry follow the order the dictionaries were added.
  Verified: importing Jitendex twice and adding both produced 12 glossary blocks
  where one dictionary produced 6, in order.
- Result ordering is by matched length, then preprocessing steps, then
  deconjugation steps, then exact-lemma match, then frequency
  (`src/lookup.cpp`). Dictionary priority does *not* enter the ranking.
- There is no remove, no disable, and no per-dictionary weight. Changing the
  order means rebuilding the `DictionaryQuery` and re-mmapping everything.

**The real gap is the glossary format.** `GlossaryEntry::glossary` is Yomitan
*structured content*: a JSON tree of tags, rubies, example sentences and CSS
class hooks, and the dictionary ships its own `styles.css`. hoshidicts hands it
over verbatim and renders nothing. Yomitan's renderer is GPL-3.0 and cannot be
copied into an MIT codebase, so this is ours to write — see the inventory below,
which turns it into a finite list.

Two smaller notes: pitch accent support is explicitly partial upstream, and the
deconjugator is a port of Jiten's, which is Apache-2.0 — permissive, but it
carries an attribution obligation that the MIT branch does not remove.

**The forks are not created.** This environment has no `gh` and no GitHub
credentials, and the organisation to fork into was not specified.
`fork-and-repoint.sh` does the whole job — fork each of the seven, verify the
pinned commit exists in our copy, rewrite every submodule URL, re-sync — and
needs one line to run:

```bash
gh auth login
ORG=<our-org> crates/nihongo-dict/fork-and-repoint.sh
```

One wrinkle it prints and that is worth knowing now: hoshidicts' *own*
`.gitmodules` still lists the upstream URLs for its six children. A `submodule
set-url` writes into `.git/config`, which does not survive a fresh clone, so
making the forks stick means committing a rewritten `.gitmodules` inside our fork
of hoshidicts and pinning our submodule at that commit. Until that is done, a
clean clone still reaches out to six upstreams.

## Attribution

`crates/nihongo-dict/NOTICE` now carries the obligations, because two of them are
not optional and one of them changes if we ship a service:

- **Jiten, Apache-2.0.** The deconjugator and its rule set are a port of Jiten's.
  Apache-2.0 wants the attribution, a copy of the licence, and a notice on
  modified files — and the rules file *is* modified downstream (the literal
  split), so that notice is now written down.
- **Yomitan.** Credited for the `.zip` layout and the structured-content format.
  No Yomitan code is used or linked, so GPL-3.0 does not attach; the credit is
  owed anyway.
- **The dictionary itself is not ours to relicense.** Jitendex is CC BY-SA 4.0,
  from JMdict (EDRDG, CC BY-SA 4.0) with Tatoeba sentences (CC BY 2.0 FR). If the
  desktop app only imports a file the user downloaded, those are the user's
  obligations. **The moment an HTTP service serves that content, they become
  ours**, attribution included, in the product UI. That is a decision to take
  before the service exists, not after.

## Recommendation

**Adopt hoshidicts, do not port only the deconjugator.**

The deconjugator is 1,965 of the 4,157 lines here, and it is the part that most
looks portable. It is also the part that would be worth the least on its own: a
deconjugator with no dictionary behind it produces 75 candidates for one word
and cannot tell which are real. The filtering that makes it useful comes from the
part-of-speech tags in the imported dictionary, so porting the deconjugator alone
means also porting the importer, the custom on-disk format, the mmap layer and
the zip/zstd handling — the other 2,192 lines — or reinventing them.

Against that, the cost of adopting is now known and it is small: three
well-understood build fixes (all automated), one nine-line patch we carry until
it is upstreamed, and a `cxx` shim that is about 90 lines because the C++ API is
nested structs that cxx cannot see through.

The two conditions from the first pass are now resolved or priced:

1. **The Linux baseline is no longer a decision.** Build in a pinned GCC 14+
   container with static libstdc++/libgcc; the binary runs on Ubuntu 24.04 LTS,
   verified end to end.
2. **The renderer is finite**: 13 tags, 53 class hooks, one style property, ten
   attributes. Still has to be written, but it can be scoped.

What the second pass adds is one design constraint, and it is the important one:

3. **The HTTP service must resolve on demand, not eagerly.** One offset costs
   2.6 ms and that is fine. Resolving whole lines costs 2.9 s of CPU per 1,000
   characters, and an LRU in front of this API does not rescue it — 7.4 % hit
   rate, unchanged when the key is truncated to the engine's own scan window.
   Caching has to happen at a layer that keys on something that repeats, and that
   layer does not exist yet. If the service is specified as "send me a line, get
   back every word in it", that decision needs revisiting before it is built.
